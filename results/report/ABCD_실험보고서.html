SLM 기반 NPC는 손님의 거짓 주장에 속지 않을 수 있는가

ABCD 실험 종합 보고서 (v4 ~ v6) · 2026-10-21 · 저장소 conference-paper (최종 커밋 123e08a)
한 줄 결론 — 판단은 SLM이 아니라 결정표(코드)가 해야 한다. SLM에게는 "손님이 무슨 주장을 했는지 알아듣기"만 맡기는 것이 가장 정확했다.
결정표 정확도 83.3%는 다른 방식보다 높았다: SLM 직접 판단 45.6%, SLM+검색 40.6%, SLM+도구 호출 63.4% (v4). 처음 보는 데이터(검증 세트)에서도 결정표 74.8%로 가장 높았다(SLM 직접 판단 41.8%, 도구 호출 64.6%). 결정표는 진짜 손님을 거부한 적이 한 번도 없었다(0%).

1. 무엇을 알고 싶었나

게임 속 상점 NPC에게 손님이 "8일 전에 할인 코드를 받았어요", "물건을 이미 반품했어요" 같은 말을 한다. 이 말은 사실일 수도, 거짓일 수도 있다. NPC는 가게 장부를 보고 다음 중 하나를 골라야 한다.

  • 믿기: 장부에 그 기록이 있고 날짜도 맞다
  • 증거 요구: 장부에 기록이 없다
  • 반박: 기록은 있지만 날짜가 다르다

연구 질문: 이 판단을 작은 언어 모델(SLM)에게 맡겨야 하는가, 아니면 코드로 된 규칙(결정표)에 맡겨야 하는가?

2. 실험 설계

2.1 데이터

  • 손님 문장: 실제 고객센터 대화 데이터셋 ABCD(Action-Based Conversations Dataset, NAACL 2021)에서 가져왔다. 손님이 첫 세 마디 안에 거래 관련 주장을 한 대화를 규칙으로 골랐다.
    • 주장 종류는 5가지: 할인 약속, 반품 완료, 이중 청구, 주문 미수령, 구매(소유)
  • 장부: ABCD에는 대화만 있고 거래 기록이 없어서, 장부는 규칙으로 합성했다.
  • 같은 문장으로 세 판을 만들었다. 손님 문장은 그대로 두고 장부만 바꾼다. 그래서 장부의 영향만 비교할 수 있다.

2.2 공정성 장치

  • 정답 분리: 정답표는 실행 코드와 다른 파일에 두었다. 실행 중에는 읽지 않으며, 테스트로 확인했다.
  • 사전등록과 봉인: 실험마다 가설·지표·채택 규칙을 먼저 문서로 쓰고, 해시로 봉인한 뒤 실행했다.
  • 반복: 모든 조건을 seed 3개(11, 29, 47)로 돌렸다.
  • 검정: 대화 원천 단위로 짝지은 sign-flip 검정(20,000회)을 했다. 여러 비교에는 Holm 보정을 적용했고, 신뢰구간은 bootstrap 95%로 구했다.
  • 모델: Ornith 1.5 9B(4비트 양자화)를 노트북의 llama-server에서 돌렸다. 모든 조건이 같은 모델을 쓴다.

2.3 비교한 방식 (판단을 어디에 맡기느냐)

조건장부 전달 방식판단 주체
F-M1P0: SLM 직접 판단그 손님의 장부 전체를 프롬프트에 넣음SLM
S-M1P0: SLM + 검색(RAG)벡터 검색으로 고른 장부 5줄SLM
T-M1P0: SLM + 도구 호출SLM이 lookup(주장 종류)을 호출하면 해당 기록을 돌려줌 (τ-bench가 평가하는 방식)SLM
F-M1P1: 결정표SLM은 주장 종류만 분류하고, 엔진이 장부를 조회함결정표(코드)

결정표 조건에서 SLM은 두 가지만 한다. 손님 문장이 어떤 주장인지 분류하는 일(이하 "귀", NLU)과 결정에 맞는 대사를 쓰는 일이다.

  • 도구가 있으면 SLM 직접 판단보다는 낫다(+17.7%p, v4). 그래도 결정표에는 못 미쳤다.

3.4 남은 오류를 줄이려는 시도

결정표의 남은 약점은 귀가 주장을 놓치는 것이다. 예를 들면 "제 할인 코드가 안 돼요"처럼 주장이 전제로 깔린 문장이다. 이를 보완하려고 두 가지를 시험했다.

시도방법결과
fail-closed (v4 후속)귀가 "주장 없음"이라 했는데 거래 단어(코드, 주문, 환불 등)가 있으면 무조건 증거 요구속음 16.3% → 0%. 대신 진짜 손님에게 확인 질문을 하는 비율이 같은 만큼 증가. 233/756회에서 사용자 판단으로 중단했고, 끝난 실행은 오프라인 예측과 100% 일치

  • 부 지표(Holm 보정)도 모두 유의했다(Holm p < .001).

4. 결론

  1. 판단은 SLM이 아니라 결정표가 해야 한다. 장부를 통째로 주든(45.6%), 검색해서 주든(40.6%), 도구로 찾게 하든(63.4%), SLM이 판단하면 결정표(83.3%)보다 정확도가 낮았다. 처음 보는 데이터에서도 순위는 같았다(결정표 74.8% > 도구 호출 64.6% > SLM 직접 판단 41.8%).
  2. SLM은 장부를 "찾는" 일은 잘하지만, 찾은 기록으로 "판단하는" 일, 특히 날짜 대조는 잘하지 못한다.
  3. 결정표의 남은 오류는 모두 "알아듣기" 단계에서 생긴다. 특히 전제로 깔린 주장에서 생긴다. 같은 SLM에게 다시 물어도 회복되지 않았다.
  4. fail-closed를 더하면 속는 것을 확인 질문으로 바꿀 수 있다. 진짜 손님을 거부하지 않는 성질은 그대로 유지된다.

논문용 요약. SLM 기반 NPC가 손님 주장을 장부와 대조하는 과제에서 판단을 SLM에 맡기는 방식(직접 판단, RAG, tool-calling)은 모두 결정표보다 정확도가 낮았다. SLM은 장부를 정확히 검색했지만, 검색 결과로 판단하는 단계, 특히 날짜 대조에서 실패했다. 판단을 결정표로 옮기자 정당한 손님을 거부하는 오류가 사라졌다. 남은 오류는 SLM이 주장을 알아듣는 단계에 집중되었다.

5. 한계

  • 합성 장부. 장부가 실제보다 깨끗하다. 또 "믿기"는 종류와 날짜가 모두 맞을 때만 나와서 구조적으로 안전하다. 실제 가게 장부에서는 이 안전성이 약해질 수 있다.
  • 모델 하나, 작은 표본. 9B 모델 하나로만 실험했고, 원천은 84개와 59개다.
  • 도구 호출을 흉내 냈다. 실제 function calling API가 아니라 JSON 출력으로 흉내 냈다. 또 τ-bench 자체를 재현한 것이 아니다.
  • 검증 세트의 비교 범위. 검증 세트에서는 SLM + 검색(RAG) 조건을 돌리지 않았다.
  • 사후 분석. 3분류 결과는 사후 탐색 분석이다.
  • 라벨 모호성. 귀가 놓친 문장 중 일부("할인 코드 언제 써요?")는 주장인지 사람마다 판단이 갈릴 수 있다.
  • 대사 품질은 평가하지 않았다.

6. 후속 연구

  • 확인 질문 이후의 대화. 손님이 코드나 주문번호를 대면 엔진이 다시 대조한다.
  • 귀(NLU) 개선: 다른 SLM, 전제된 주장의 예시 추가. 결정이 귀의 출력만으로 정해지므로 저비용으로 비교할 수 있다.
  • 명시적 주장과 전제된 주장을 나눈 라벨링과 결과 보고
  • 실제 거래 데이터와 실제 function calling으로 재검증
