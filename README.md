# 상점 NPC는 손님 말을 어디까지 믿어야 할까

**온디바이스 소형 언어모델(SLM) 상인 NPC의 "플레이어 주장 오염" 실험**

게임 속 잡화점 주인 NPC "도르만"에게 손님(플레이어)이 증거 없이 이렇게 말한다고 해 보자.

> "저 어제 달빛 잼 예약했잖아요." · "선금 이미 냈어요." · "할인해 준다고 약속하셨죠?"

NPC가 이 말을 그대로 믿고 기억하거나, 물건을 내주거나, "네, 맞아요"라고 대답해 버리는 것을 이 저장소에서는 **오염(contamination)** 이라고 부른다.
이 저장소는 오염을 줄이는 방법을 단계적으로 실험한 코드, 시나리오, 원자료, 결과 보고서를 담고 있다.

- 모델은 모두 노트북에서 돌아가는 로컬 모델이다(llama.cpp). 외부 API는 쓰지 않았다.
- 실험은 모두 **사전등록**(실행 전에 가설, 지표, 판정 규칙을 문서로 봉인) 후 실행했다. 사전등록 문서는 `docs/`, 결과는 `results/`에 있다.
- 논문과 발표자료의 수치는 손으로 쓰지 않고 결과표에서 자동 생성한다(`npc.verify_paper`가 대조).

---

## 핵심 아이디어: 장부, 문지기, 귀, 입

| 비유 | 실제 구성 | 하는 일 |
|---|---|---|
| **장부** | 게임 엔진(SQLite) | 재고, 예약, 골드 같은 "진짜 사실"의 유일한 주인. 모델은 장부를 고칠 수 없다 |
| **귀** | NLU(모델) | 손님 말이 어떤 주장인지 알아듣는다(예약, 선금, 약속...) |
| **문지기** | 승격 정책(결정표 코드) | 그 주장을 믿을지, 증거를 요구할지, 반박할지 정한다 |
| **입** | 대사 생성 | 손님에게 실제로 하는 말 |

조건 이름은 `M`(기억) + `P`(정책) 조합이다.
- `M0` = 대화를 섞어 담는 Vector RAG 기억, `M1` = 출처가 붙은 구조화 기억
- `P0` = 모델이 직접 결정, `P1` = 코드 결정표가 결정, `P2` 이후 = 대사 쪽 개선

## 실험 흐름 한눈에 보기

### 1부. 한국어 판타지 상점 (EXAONE-3.5-2.4B)

| 단계 | 바꾼 것 | 결과 | 한 줄 결론 |
|---|---|---|---|
| 본실험 M0P0 / M1P0 / M1P1 | 기억 구조화, 코드 결정표 | 오염률(CCR) 0.30 / 0.21 / 0.26, 결정 일치율 0.53 / 0.48 / 0.83 | 오염을 줄인 건 **기억 구조화**였고, 결정표의 효과는 **결정을 정확히 구분**하는 데서 나왔다 |
| 공정비교 M0P0R / M1P0R | 결정표를 프롬프트로 알려주기만 함 | 일치율 0.65 / 0.72 | 알려주기만 해서는 코드로 집행하는 것(0.83)을 못 따라간다 |
| M1P2 → M1P2G | 대사 프롬프트에 장부 근거를 넣음 | 정규식 탐지 47 → 28 → 16건 | 줄었지만, 장부를 들고도 지어내는 말은 남았다 |
| M1P3 | 최종 대사를 엔진 사실 템플릿으로 조립 | 최종 출력 오염 0건 | 모델이 좋아진 게 아니라 **입의 권한을 제한**한 설계 효과 |
| 원인 분리, 적대적 검정, M1P4 | 고위험 무증거 시나리오, fail-closed | 결정표의 실패 7건이 **전부 귀(NLU) 오독** | 병목은 문지기가 아니라 귀였다 |
| M1P5 ~ M1P9, NLU V3 ~ V9 | NLU 지시문, 2단계, kNN 등 | 대부분 유의하지 않음 | 지시문 손질로는 귀를 크게 못 고쳤다 |
| **M1P10** | 오염 채점 방식부터 검증, 모델 대사 vs v2 템플릿 | 모델 대사 **12.6%** vs 템플릿 **0%** (p = 0.00012) | 판단은 엔진이, 말은 검증된 문장이 하게 나누면 오염이 사라진다 |

M1P10에서 알게 된 점: 그전까지 쓰던 정규식 채점기는 처음 보는 대사에서 재현율이 0.34밖에 안 됐다. 그래서 두 언어모델의 이중 판정과 조정 절차(`docs/오염_코드북.md`)로 바꿨고, 그러자 실제 오염 크기(약 8번에 1번)가 제대로 보였다.

### 2부. ABCD 영어 자연 발화 (Ornith-1.5-9B)

연구자가 직접 쓴 한국어 시나리오만으로는 일반화를 말하기 어려워서, 실제 사람이 쓴 고객 상담 문장(ABCD 데이터셋, MIT)으로 다시 시험했다.
고객 문장 84개마다 **장부에 기록이 있는 판(v)** 과 **없는 판(n)** 을 짝지어 168개 시나리오를 만들었다.

| 단계 | 바꾼 것 | 기록 있는 주장을 거절한 비율 (낮을수록 좋음) | 기록 없는 주장을 받아들인 비율 |
|---|---|---|---|
| 1차 M1P0 vs M1P1 | 모델 결정 vs 결정표 | 모델 90.5% / 결정표 0% | 모델 0.4% / 결정표 16.3% |
| 2차 L2 | 장부 형식 + 지시문 수정 | 76.2% | 0% |
| 3차 L3 | 오늘 날짜를 넣고 날짜를 맞춘 장부 | **54.4%** | 0% |
| 3차 L4 | 같은 장부를 벡터DB로 검색해 5줄만 제공 | 79.0% | 2.4% (아래 결함, 제외 시 0%) |

- 모델은 **지나치게 의심이 많았다.** 장부에 기록이 있어도 대부분 거절했다. 장부를 알아보기 쉽게 만들수록 나아졌다.
- 결정표의 실수(16.3%)는 전부 귀가 주장을 "주장 없음"으로 잘못 읽은 경우였다. 1부와 같은 결론이다.
- 벡터DB 검색은 근거 줄은 대부분(91.7%) 찾아왔지만, 손님 본인의 다른 기록이 빠지고 다른 손님 기록이 평균 2.9줄 섞여서 오히려 나빠졌다.
- **L4에는 설계 결함이 있다.** 같은 손님 이름·계정이 여러 원천에 나뉘어 들어가 있어서(계정 9개, 원천 27개), 벡터DB가 "기록 없음" 조건에서도 같은 계정의 다른 기록을 찾아왔다. L4가 기록 없는 주장을 받아들인 6건은 전부 여기서 나왔다. 겹치는 계정 원천과 앞서 문제가 된 원천(A003, A044, A068)을 모두 빼면(남은 원천 54개) 그 수용은 0건이 되고, L3(59.3%)가 L4(77.8%)보다 낫다는 결론은 그대로다(p = 0.006).
- 이름만 같고 계정이 다른 손님의 줄도 검색됐다(주장 턴 합계 v 678줄, n 837줄). 예를 들어 A072n은 장부가 비어 있는데도, 다른 계정의 구매 기록을 근거로 "장부에 구매가 있다"고 말했다. 결정은 증거 요구였으므로 수용 0건이라는 결과는 맞다. 하지만 대사까지 오염되지 않았다는 뜻은 아니다.
- 그 밖에 날짜 파싱 오류 1건과 L4 검색 질의 문제(6개 원천)도 사후 검토에서 나왔다. 모든 제외 분석은 `results/abcd3/report.md`에 있다.

### 2부 4차: 정답 분리 실험 (ABCD v4)

앞선 1~3차에는 정답 정보(`verified:` 표시)가 모델 입력에 새는 문제가 있었다. 4차는 구조를 바꿔 다시 했다(`docs/ABCD_v4_사전등록.md`, `results/abcd4/report.md`).

- 시나리오 파일에는 대화와 손님만 있고, 정답은 `answer_key_abcd4/answer_key.csv`에만 있다. 실행 코드는 이 파일을 열지 않는다.
- 가게 장부는 하나다(`ledger_abcd4/shop_ledger.csv`). 같은 문장을 세 손님이 말한다: 기록 있음(v), 없음(n), 날짜가 어긋남(d).
- 손님이 말한 날짜는 대화문을 고치지 않고 별도의 `date` 필드로 준다(원문에 이미 날짜 표현이 있는 문장도 있다). 결정표는 장부를 직접 조회해 판단한다.

| 조건 | 기록 있음 v | 기록 없음 n | 날짜 어긋남 d |
|---|---|---|---|
| 모델이 결정 (손님 장부 전체) | 52.8% | 56.3% | 27.8% |
| 모델이 결정 (장부 검색 5줄) | 32.9% | 76.6% | 12.3% |
| 결정표가 결정 (손님 장부 전체) | **91.3%** | **83.7%** | **75.0%** |

(결정 정확도, 높을수록 좋음. 2,268회, seed 3개)

- 결정표는 정확도 83.3%로, 모델(45.6%)보다 37.7%p 높았다(p < .001). 사전등록 채택 규칙을 충족했다.
- 다만 **기록 없는 주장을 받아들인 비율은 결정표가 더 높았다**(16.3% vs 2.0%). 봉인된 채점표 기준으로 결정표의 오답 126건은 전부 귀(NLU)가 주장 종류를 잘못 읽은 경우였다. 다만 채점표 자체에도 결함이 1건 있다(A064는 손님 말의 날짜와 날짜 필드가 어긋남). A064를 빼도 결론은 같다(차이 37.8%p, `results/abcd4/report.md`).
- 모델은 장부를 보고도 날짜 차이를 거의 짚지 못했다(d 정확도 27.8%).

## 알려진 한계

1. 오염 판정은 사람이 아니라 언어모델 두 개와 조정자가 했다. 사람과의 일치도는 아직 낮다(κ 0.54).
2. 한국어 시나리오의 정답 라벨 체계는 사용자 점검에서 문제가 지적되어 재검토가 필요하다.
3. ABCD 실험의 모든 조건에 기억의 `verified:` 표시가 있어, 개선이 장부 덕인지 이 표시 덕인지 구분하지 못한다.
4. NPC 1명, 상점 1개, 폐쇄된 세계다. 일반화를 주장하지 않는다.
5. `paper/draft.md`는 본실험 단계(10-13) 기준이다. 이후 결과는 아직 반영하지 않았다.

## 재현 방법

```bash
# 1. 추론 서버 (모델 파일은 models/README.md 참고)
llama-server -m models/EXAONE-3.5-2.4B-Instruct-Q4_K_M.gguf \
             --host 127.0.0.1 --port 8080 -c 4096 -ngl 99 --jinja
llama-server -m models/bge-m3-FP16.gguf \
             --host 127.0.0.1 --port 8081 --embedding --pooling cls -c 8192 -ngl 99

# 2. 구조 불변조건 테스트
python3 -m pytest tests/ -q

# 3. 본실험 (18 시나리오 x 3 조건 x 3 seed, 중단 후 --resume 가능)
python3 -m npc.cli runall --conditions M0P0 M1P0 M1P1 --resume
python3 -m npc.cli run --condition M1P1 --scenario S05_v1 --seed 11   # 대화 하나만 보기

# 4. 지표 -> 논문 -> 수치 검증 -> PDF
python3 -m npc.eval
python3 paper/make_draft.py --metrics results/metrics_pre_m1p2.csv
python3 -m npc.verify_paper --metrics results/metrics_pre_m1p2.csv
python3 paper/make_pdf.py
```

공통 설정: temperature 0.2, top_p 0.9, seed 11 / 29 / 47.

### 설계로 보장한 것 (연구 성과가 아님)

SQLite CHECK 제약으로 다음 두 가지를 DB 단에서 막았다(`tests/test_atomicity.py`).
- 모델이 만든 문장은 기억으로 승격될 수 없다(`generated_text.memory_eligible = 0`).
- 게임 사실의 출처는 엔진뿐이다(`world_truth.source = 'game_engine'`).
