# ABCD v6 사전등록: 도구 호출(tool-calling) 기준선 T-M1P0

계획: `../.omo/plans/abcd-v6-toolcall.md`. 사용자가 2026-10-20에 승인했다.
실행 전에 `python3 abcd6_live.py seal`로 봉인한다. 봉인 파일은 `results/abcd6/prereg_seal.json`이고, 이 문서와 v4·v5 봉인 파일의 해시를 담는다.

## 목적
τ-bench가 평가하는 tool-calling 에이전트 방식, 곧 LLM이 DB 조회 도구를 스스로 호출하고 직접 판단하는 방식을 이 과제에 구현한다. 그리고 결정표(F-M1P1)와 비교한다. τ-bench의 과제나 수치를 재현하는 것은 아니다.

## 조건: T-M1P0
F-M1P0과 같다. 페르소나, NLU, 결정 지시문, 결정 스키마, seed가 모두 같다. 다른 점은 장부를 전달하는 방식뿐이다.
1. **장부 머리말만 준다**: 재고, 오늘 날짜, 손님 이름과 계정. 기록 본문은 보여 주지 않는다.
2. **도구 단계**: LLM이 `{"call": bool, "claim_type": 술어 5종 | "none"}`을 낸다. 지시문은 `abcd4_runner.TOOL_INSTRUCTION`이다.
3. **엔진 처리**: `call`이 참이고 술어가 유효하면, 이 손님 계정에서 그 종류에 맞는 장부 행을 그대로 돌려준다. 판정(기록 있음 / 없음 / 불일치)은 돌려주지 않는다.
4. **판단 단계**: `[Tool result]`를 붙이고, F-M1P0과 같은 결정 지시문으로 결정과 대사를 낸다.
- **구현 방식**: llama-server의 tools API가 아니라 JSON 구조화 출력으로 도구 호출을 흉내 낸다. 이 점은 한계로 보고한다.

## 데이터와 실행
- **v4 (84원천)**: 252개 시나리오 × seed 11/29/47 = 756회
- **v5 검증 세트 (59원천)**: 177개 시나리오 × seed 3개 = 531회
- **비교 대상**: 봉인된 기존 실행 기록을 쓴다.
  - v4: F-M1P0, S-M1P0, F-M1P1
  - 검증 세트: F-M1P1
- **서버·모델**: v4와 같다.

## 지표
분석 단위는 주장 턴이다. 원천마다 판과 seed를 평균한 뒤, 짝지은 sign-flip을 20,000회 한다. 신뢰구간은 bootstrap 5,000회로 구한 95% 구간이다.
- **주 지표**: 정확도 차이(F-M1P1 − T-M1P0). v4와 검증 세트를 각각 검정하고, 두 검정에 Holm 보정을 한다.
  - "결정표가 더 낫다"의 기준: Holm p < .05이고 차이 > 0
- **부 지표 (Holm 보정)**:
  - (a) T-M1P0 − F-M1P0 정확도, v4
  - (b) d 반박 정답률, F-M1P1 − T-M1P0, 세트별
  - (c) n·d 잘못 수용률, F-M1P1 − T-M1P0, 세트별
- **기술 통계**:
  - 도구 호출률
  - 고른 종류가 정답 술어인 비율
  - 도구 단계 형식 실패 수
  - 판별 결정 분포
  - 수용/보류/거부 3분류 표(`docs/ABCD_3way_사후분석.md` 기준)

## 중단 규칙
시범 실행은 v4 원천 A001, A021, A041, A061 × v/n/d × seed 11로, 12회 돌린다. 시범 결과는 본 실행에 포함한다. 다음 중 하나라도 해당하면 멈춘다.
- 생각 과정 누출
- 영어가 아닌 응답
- 도구 단계 형식 실패 2회 이상
- 도구 결과에 다른 손님의 행이 들어감
- 프롬프트에 판정 결과가 들어감
