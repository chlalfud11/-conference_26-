# NLU 개선 실험 (M1P5) 사전등록

작성: 2026-10-15. 상태: 이 파일과 `nlu_improve.py`의 해시를 `logs/nlu_improve/freeze.json`에 동결한 뒤에 첫 추론을 한다.

## 1. 배경 (진단, 추론 0건)

`python3 bottleneck_diagnosis.py` → `results/bottleneck/diagnosis.json`

- M1P1에서 NLU가 위험도(고위험/저위험)를 맞힌 채점턴 297개는 결정이 297/297 정답이다. 결정 오답 54개는 모두 NLU가 위험도를 틀린 턴에서 나왔다.
- 채점턴 고유 NLU 354회: 위험도 정확도 0.839, 술어 정확도 0.494. 고위험을 저위험으로 읽은 경우가 25건(오염 원인), 저위험(소문)을 고위험으로 읽은 경우가 32건(TCAR 손실 원인)이다.
- 따라서 코드 정책 조건의 결정 성능 병목은 NLU 위험도 판독이다. 정책 표나 임계값은 바꾸지 않는다.

## 2. 개입 (모델·seed·스키마·정책 동일, NLU 지시문만 변경)

- **B**: 기존 `runner.NLU_INSTRUCTION`과 지금 발화. 기준선이며 같은 서버 세션에서 다시 실행한다.
- **V1**: 출처(손님 자신의 가게 거래 vs 남에게 들은 소식)를 먼저 보도록 정의를 다시 쓰고, 일반 예시 11개를 넣는다. 예시는 시나리오에 나오지 않는 물건(밧줄, 등불 기름, 양초, 약초, 칼)으로 새로 썼다. 단, dev(v1) 발화를 본 뒤에 작성했다.
- **V2**: V1과 같고, 같은 대화의 직전 손님 발화 최대 2개를 문맥으로 함께 준다. NPC 대사는 넣지 않는다.
- 문구 원문: `nlu_improve.py`의 `V1_INSTRUCTION`, `V2_SUFFIX`, `messages_for`.

## 3. 데이터 분할

- dev = `*_v1` 9편, test = `*_v2`, `*_v3` 18편. 채점턴만 쓰고, seed는 11·29·47이다.
- 오프라인 지표: NLU 결과를 M1P1 정책(`config.expected_decision`)에 넣었을 때의 결정 일치율. 보조 지표는 위험도 정확도, 고→저 건수, 저→고 건수, TCAR, 기준① 건수, NLU 지연이다.

## 4. 선택 규칙 (dev만 사용, test 호출 전에 `logs/nlu_improve/selection.json`에 기록)

1. V1과 V2 가운데 dev 일치 건수가 가장 많은 변형을 고른다. 동점이면 고→저 건수가 적은 쪽, 그래도 같으면 V1을 고른다.
2. 고른 변형의 dev 일치 건수가 B보다 **엄격히 크면** 라이브를 진행한다. 아니면 라이브를 하지 않고 null로 보고한다.
3. test에서는 B, V1, V2를 모두 평가하고 전부 보고한다. test 결과로 선택을 바꾸지 않는다.

## 5. 라이브 M1P5

- 경로: `runner.run_dialogue(scenario, "M1P1", seed)`에서 `_nlu`만 선택 변형으로 교체한다. 발화 프롬프트, 기억, 정책은 M1P1과 같다.
- 동일 경로 증명: B를 끼우고 스텁 모델로 M1P1 기록을 재생해, 81런의 프롬프트 해시 순서가 모두 일치하는지 확인한다(`replay_check.json`).
- 27편 × 3 seed = 81런을 1회 실행한다. 결과를 보고 시나리오·seed·변형을 추가하지 않는다. 중단되면 빠진 run_id만 재개하고 그 사실을 공개한다.

## 6. 라이브 분석 (`nlu_improve.py analyze`)

- **주 가설**: M1P5의 결정 일치율이 M1P1과 다르다. 시나리오별 일치율 차이에 대한 부호뒤집기 순열검정(양측, α=0.05)을 쓴다. 0이 아닌 차이가 20개 이하이면 정확 계산, 그보다 많으면 100,000회 표본(seed 20261015)이다. 부트스트랩 95% CI는 10,000회로 구한다.
- **부 가설 3개 (Holm 보정)**: 기준① 비율(부호뒤집기), 기준② 비율(부호뒤집기), TCAR(Fisher 양측).
- 기술 통계: NLU 위험도 정확도, 턴 지연 중앙값과 p95.

## 7. 미리 밝히는 한계

1. v1과 v2·v3는 같은 장면을 다르게 표현한 변형이라, dev에서 본 표현이 test로 새어 들어갔을 수 있다. 장면 단위 일반화는 주장하지 않는다.
2. V1 예시 일부(예: "제 귀로 들었어요" → promised_reward)는 dev 오류를 보고 넣었다.
3. M1P1 기준 로그는 이전 서버 세션에서 나왔다. 그래서 라이브 비교에는 서버 재기동에 따른 비결정성이 섞인다.
4. V2는 손님 발화 문맥을 쓰기 때문에, 문맥 판단이 필요한 후속 발화 라벨에서 유리하다. 이것은 의도한 효과이고 라벨 설계를 바꾸지 않는다.
5. 시나리오 대사는 `draft_pending_user_approval` 상태다.
6. 지연시간은 NLU 지시문이 길어질수록 늘 수 있으며, 그대로 보고한다.
